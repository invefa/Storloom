## Current implementation

### Performance and resumable reading exports

Backup selection and header inspection run on a worker; rendering reuses their immutable result. The actual export revalidates its manifest and backup. Reader assembly serializes each message once, caches conversation IDs, and batches append-only spools with an 8 Mi-character buffer budget rather than opening a file for every interleaved message. A local synthetic 30,000-message / 128-interleaved-conversation comparison reduced assembly from about 13.4 seconds to under 1 second. This is a stage benchmark, not a real-backup completion-time promise.

Verified-backup exports create `export-progress.json` and retain committed JSON spools inside their own `.work-*` directory after interruption. Completed databases are reused; an interrupted database that has not committed restarts. Reader progress is committed about every 30 seconds, on safe cancellation, and at phase boundaries; finished conversation pages are reused. Resume validates backup identity, settings, file sizes and SHA-256 prefixes, verifies existing media, and discards only uncommitted output tails. It refuses altered checkpoints, incompatible inputs and concurrent writers. Keys are never stored: encrypted backups require a newly supplied or captured key. Decrypted database working files are removed after cancellation.

In the GUI, load the same raw backup, obtain its key if needed, click **Resume reading export**, and choose the interrupted reading-export folder. CLI: `chat-export --platform QQ --backup MANIFEST.json --destination EXISTING_FOLDER --resume` with the same image/language settings and key options. Keep `export-progress.json` and `.work-*` together; these contain private chat export data. Successful completion removes temporary spools. Exports started before version 0.6.7 have no checkpoint and cannot be adopted by this feature. Running tasks are not upgraded in place.

The operation bar remains visible while working, with a phase percentage or an activity indicator when totals are unknown. Resume throughput and ETA use work completed since the resume, excluding already completed messages.

Version 0.6.8 additionally tracks whether each conversation arrives in timestamp order. Ordered spools stream directly into pages; unordered conversations retain bounded external sorting, with an in-memory path for small conversations. Checkpoints from 0.6.7 lack this ordering metadata and retain the sorting path. A local synthetic 30,000-message / 128-conversation run including checkpoints improved from 3.12 to 2.34 seconds; generated reader files matched byte for byte. This does not establish real-backup throughput.

The same worker setting now also bounds independent conversation pagination (1–4 workers), with message order preserved within each conversation and synchronized checkpoint commits. In that synthetic run, 2 workers took 1.86 seconds and 4 took 1.45 seconds. More workers can increase disk contention; these measurements do not promise a speedup for a particular backup drive. Settings apply to newly started exports, including resume invocations.

QQ account discovery, key validation and reading export select the main `nt_qq/nt_db/nt_msg.db` independently of filesystem enumeration order. QQ Guild's identically named database uses a separate key: it remains in the raw backup, is excluded from the main-chat reader, and is recorded as an unsupported database in the export report. A reading export containing such a database is reported incomplete.

Wrapped NTQQ databases can include preallocated zero-filled space beyond the logical SQLite page count. Storloom reads that count from the authenticated first page only when its change counter matches the version-valid-for counter, checks every byte beyond that boundary is zero, and excludes that padding from the decrypted working copy. Active pages still require authentication; stale size headers, truncated databases and nonzero tails are rejected. The source and raw backup remain unchanged. Failed or partial exports display their errors and do not report a successful operation; a failure with no exported databases does not offer an empty reader.

Storloom uses .NET cryptography, Windows `winsqlite3.dll` for read-only SQLite queries, ZstdSharp.Port for modern compressed message bodies, and K4os.Compression.LZ4 for legacy compressed content. The adapted C# capture component is isolated under `Chats/NativeCapture`; its license is in the third-party notices. Runtime operation does not fetch upstream tools or execute downloaded scripts.

| Area | Implemented | Limits |
| --- | --- | --- |
| Raw archive | Whole selected account folder, databases/WAL/media included, SHA-256 verification, sidecar manifest | Close QQ/WeChat first; no client path rewrite, junction, or automatic removal |
| WeChat 4.x DB | 4096-byte pages, SHA-512 page authentication, raw 32-byte key or PBKDF2-SHA512 256000, reserve 80; Msg_* and Name2Id tables, Zstd bodies | Client-specific schemas/keys may change; conversation table hashes may remain as IDs |
| WeChat 3.x DB | PBKDF2-SHA1 64000, reserve 48; MSG table text/XML and bounded LZ4 content | No legacy key extraction guarantee; contact names and sender resolution are incomplete |
| NTQQ DB | nt_msg.db, wrapper 1024 or 0, PBKDF2 4000, authenticated SHA-1/SHA-512 compatibility combinations; direct/group message tables; text/attachment protobuf fields | Legacy pre-NTQQ formats and every protobuf element are not supported. Exact wrapped Windows zero lock-page exception is handled; other authentication failures refuse export |
| WAL | Header/frame checksums, salts, page authentication, last committed frame and database size | Uncommitted tails excluded; malformed committed frames fail. This is not a live-database snapshot service |
| Output | Streaming JSONL with original binary payloads, typed offline HTML message cards, completeness report; conversations sorted across shards | Available contact metadata only; no guaranteed decoding of every message field or media format |

`Complete` means all discovered **supported message databases** were read without reported errors, at least one message was emitted, and no unsupported messages or unresolved expected media were recorded. It does not certify every structured field, undiscovered database families, playback codecs, or restorability. Identical messages are retained rather than heuristically deduplicated. An unsupported schema/key/page produces a failure or incomplete result rather than a fabricated empty transcript.

## Keys and consistent snapshots

QQ also has an explicit **Start QQ login capture** action. Exit daily QQ first, select its installed Tencent-signed QQ.exe, and log in to the new instance. Storloom verifies the matching wrapper.node signature, resolves the x64 key function from its string reference and PE runtime-function table, checks the loaded module path and code before setting a breakpoint, and accepts only a key authenticating the selected backup. It never starts this debugger as an automatic fallback. This follows the [QQDecrypt Windows method](https://github.com/QQBackup/QQDecrypt/blob/main/docs/decrypt/extract/NTQQ%20%28Windows%29.md), using an adapted MIT chatlog-keeper C# debugger with key logging removed. Upstream version verification is not a guarantee that Storloom capture has been validated on every client. Capture waits up to 90 seconds and runs in the isolated worker; cancellation or timeout ends the worker and its debugged instance.

The GUI guides account selection -> verified raw backup -> readable export. Raw backup needs no key. After making the snapshot, you can reopen the client to read a key against the archived database.

1. Choose an account directory you own. Automatic discovery checks known current-user locations; relocated data can be inspected manually. The size column reports the whole account directory, including media; partial scans are marked as a lower bound.
2. If required, use **Read key (passive)** while logged in. It reads only current-user QQ/WeChat process memory, has a bounded search, and accepts a candidate only after database HMAC authentication. It does not modify the process. This does not find every version's keys. Some newer WeChat builds do not retain the supported heap representation after login; use the separate login-capture action in that case. Starting the client alone is not sufficient.
3. WeChat 4.x has a separate explicit **login capture** action. Close daily WeChat first, select installed Weixin.exe, and log in to the new child instance. Storloom validates locally trusted Tencent Authenticode signatures on the executable and Weixin.dll, checks a supported fingerprint, and uses the adapted native debugger component only for that child. It does not attach to an already-running client. A separate worker hosts the debugger and exits after capture; Windows then ends its newly created client tree. The native login wait is bounded to 90 seconds and the worker has a two-minute outer deadline. Cancellation ends that worker. This is an explicit, version-dependent operation; the daily client must already be closed. The raw snapshot exporter handles committed WAL data after the capture instance exits.
4. Alternatively paste a key into the masked field: WeChat 64 hexadecimal characters, NTQQ 16 or 32 printable ASCII characters. This is the chat database encryption key, not a QQ/WeChat login password. The CLI reads a private `--key-file`, never a key in the process command line. Captured keys are never saved or logged; mutable byte buffers are zeroed after use. .NET strings, OS paging/crash dumps, and user-created key files are outside a promise of perfect memory erasure.
5. Close the source client for the **raw backup**. After verification, reopen it if needed to read a key and export the offline archive. A verified sidecar allows offline export even when the original client is later running. CLI: `chat-export --platform WeChat --backup MANIFEST.json --destination NEW_FOLDER --key-file PRIVATE_FILE`.

Exports are plaintext and should be protected like the original conversation. Private working decrypted databases are removed on normal completion, cancellation, and handled failures. An OS/process crash can leave `.work-*` files in the chosen export directory; inspect and remove them after confirming no export is running. Partial export reports remain explicitly incomplete. No chat content is uploaded.

## Validation status and space reclamation

Automated tests use synthetic encrypted QQ/WeChat pages, committed WAL frames, SQLite message databases, tampering, cancellation, duplicate messages, and HTML escaping. No personal account transcript is checked into source or tested by CI. Real-client login capture, every active QQ/WeChat release, large-account performance, contact/media decoding, and restore compatibility need version-specific manual validation.

Raw backup and readable export preserve originals. To reclaim space later, first verify the raw archive and retain the manifest, then deliberately plan a separate Move of the desired folder to a fresh destination or use client-supported storage management. Storloom does not infer that readable export makes chat data disposable. There is no one-click deletion of an account after export and no cross-version client restore guarantee.

## Conversation reader implementation

The reader uses an original C# export pipeline and local HTML/CSS/JavaScript; no external exporter is embedded. Research considered [WeChatMsg](https://github.com/LC044/WeChatMsg), [wxdump_web](https://github.com/xaoyaoo/wxdump_web), and [wechat-decrypt contact resolution](https://github.com/freanocank/wechat-decrypt/blob/main/contacts.py). Conversation-oriented navigation and remark-first names are interaction/data ideas; no source from these viewers is redistributed.

WeChat 4 message table names are matched to Name2Id usernames by MD5; sender row IDs are resolved separately within each database. Supported contact and legacy rcontact tables provide remark/nickname/alias names. Unrecognized schemas fall back to stable IDs. NTQQ names are available only when a supported contact table is present.

The offline reader loads one 300-message page at a time. An external merge orders conversations without loading all messages into memory. Lossless message text and available binary payloads remain in messages.jsonl and collapsed source disclosures; long reading text is not truncated. Content filters apply to the current page; the cancellable next-match action searches later pages. Local media resolution accepts unambiguous local references, copies assets by content hash, and decodes legacy XOR image containers. V1 AES images and V2 images with validated offline-derived keys are supported. The desktop exporter also reads image-key candidates from the current user's standard WeChat configuration; CLI users opt in with --local-image-keys. Derived keys stay in memory and are cleared when the export ends. Packed database references locate additional images/videos. Unsupported full-size images can fall back to a labelled thumbnail, which keeps the result incomplete. WXGF animations, encrypted emoticon caches, VoiceInfo/SILK audio and document attachments are covered below; resource-index-only references and other unsupported image layouts remain explicit gaps. Unavailable expected media increments unresolvedMedia; unknown messages increment unsupportedMessages. Either marks the reading result incomplete. See [message display coverage](message-display.md).

The viewer uses text nodes and JSON serialization rather than interpolating message HTML. Its CSP forbids remote loads. The embedded WebView2 host disables host objects, unsolicited downloads, permissions, frame navigation, and external navigation; its origin-restricted message bridge permits bounded copy/save actions, and serves only bundled viewer assets and the selected archive directory. The browser fallback remains fully local.

Database processing uses a configurable bounded 1-4 worker pool. Ordinary SQLite readers share a read lock; large shifted NTQQ databases exclusively lock the process-global pending-byte setting. AES/MAC context is reused per database and WAL; page authentication and committed-WAL checks remain mandatory. Transfers hash sources during copying, then verify every destination once against those hashes before publishing the complete batch. This removes the redundant per-file target read. Copies and pre-removal move checks remain separate safety stages. Full verification when creating the raw backup is retained. Before reading export, database keys are authenticated first. The default-on recheck of every backup file can be disabled in the GUI or with CLI `--skip-backup-verification` (for `--backup` exports). Skipping it retains receipt/path/size checks, database page/WAL authentication and checks on copied media, but may miss subsequent changes to other files. `backupReverified` and `verifiedBackupBytes` in the export report record whether the full recheck ran; reading completeness does not certify skipped checks. Phase timings and synthetic performance results are diagnostic evidence, not a promise of HDD or real-client throughput.

## WeChat resource recovery

Built-in face aliases accept bracket, slash and configured names on both platforms. WeChat encrypted emoticon caches use account-specific AES-CBC keys derived from local configuration; these keys remain in memory. WXGF/HEVC animations can be converted to local GIF previews when `ffmpeg.exe` is installed on PATH. Conversion is isolated, cancellable and bounded by time, dimensions and output size. FFmpeg is optional and is not redistributed. Conversion failure leaves the resource explicitly unavailable; no network fallback fetches private CDN URLs.

VoiceInfo payloads in media databases are matched using the database-local Name2Id mapping, conversation and unsigned server message ID. Conflicting payloads are rejected. The pinned, separately built SILK helper produces 24 kHz mono WAV; missing or unsupported voices remain unresolved. Document and archive attachments use the same unambiguous local lookup and streamed, hashed copying as media. Resource repair adds immutable hashed assets and sparse reader-index associations without rewriting messages.jsonl or conversation pages. The original export report remains historical and incomplete status is preserved. Raw backups are never modified. Resources absent from the backup cannot be reconstructed.

Build the Windows x64 SILK helper with `scripts/Build-Silk.ps1` (GCC/MinGW required). The script verifies the pinned upstream archive SHA-256 and retains MIT/Skype SDK notices. Release packaging includes this helper in GUI and CLI directories plus notices. See [SILK decoder source](https://github.com/kn007/silk-v3-decoder/tree/507be6bca8ce1fb977a061481f1d79e8c610e309), [emoticon cache research](https://github.com/yanyanbabyi/Wechat-Emoticon-Parser-fix) and [media database mapping](https://github.com/qiaodogbear/ChatTrace).
