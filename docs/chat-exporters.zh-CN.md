## 当前实现

### 性能与断点续导

选择备份、读取清单和检查数据库头改在后台进行，页面重绘复用不可变结果；真正导出时仍会重新核对清单和备份。阅读版组装只序列化每条消息一次、缓存会话标识，并以最多 8 Mi 个字符的缓冲批量追加会话文件，避免会话交错时逐条开关文件。本机模拟 128 个会话交错的 3 万条消息，组装阶段从约 13.4 秒降至不到 1 秒。这只是阶段基准，不代表实际备份的总耗时。

从已验证备份导出时会创建 `export-progress.json`，中断后保留该导出自身 `.work-*` 目录内已提交的 JSON 中间结果。已完成的数据库直接复用；尚未提交的当前数据库需要重新处理。阅读版进度约每 30 秒、安全取消及阶段边界保存一次，已完成的会话分页可以复用。续导会核对备份标识、设置、文件大小和 SHA-256 前缀，验证已有媒体，并仅回退尚未提交的输出尾部；检查点被改动、输入不匹配或另一个写入任务仍在运行时会拒绝续导。密钥不会保存，加密备份需要重新提供或读取密钥。取消后会清除解密数据库工作文件。

界面操作：载入同一份原始备份，按需重新取得密钥，点击“继续上次导出”，选择上次中断的阅读版目录。CLI 使用 `chat-export --platform QQ --backup MANIFEST.json --destination EXISTING_FOLDER --resume`，并保持相同的图片、语言及密钥选项。请一起保留 `export-progress.json` 和 `.work-*`，它们包含私密聊天导出数据；成功完成后会清理临时中间结果。0.6.7 之前启动的导出没有检查点，无法接管续导；运行中的任务不会被原地升级。

任务进行时持续显示当前阶段进度条和百分比，无法得知总量时显示活动条。续导的速度与预计剩余时间按本次新完成的工作计算，不把上次已完成的消息计入速度。

0.6.8 还会记录会话消息是否已按时间排列。有序会话直接流式生成分页；乱序会话保留有界外部排序，小会话可以在内存中排序。0.6.7 的检查点没有排序元数据，续导时仍走排序流程。本机模拟 3 万条消息、128 个会话并开启断点记录，总耗时由 3.12 秒降至 2.34 秒，生成的阅读版文件逐字节一致；这不代表真实备份的吞吐量。

同一并发设置现在也控制独立会话的分页生成（1–4 个工作线程），同一会话内保持消息顺序，检查点提交同步处理。上述模拟用例使用 2 个线程约 1.86 秒，4 个线程约 1.45 秒。增加线程可能加剧磁盘争用，不能保证在某块备份盘上提速。设置作用于之后新启动的导出及续导任务。

QQ 账号发现、密钥验证和阅读版导出统一选择主聊天的 `nt_qq/nt_db/nt_msg.db`，不依赖文件系统枚举顺序。QQ 频道同名数据库使用独立密钥：原始备份保留它，主聊天阅读版不混入它，导出报告会列为未支持的数据库并标记阅读版不完整。

带封装头的 NTQQ 数据库可能在 SQLite 有效页数之后预留全零空间。程序只在首个认证页的更改计数与版本有效计数一致时采用其有效页数，并逐字节检查尾部全零，将这些预留空间排除在解密工作副本之外。有效页仍须认证；失效的页数头、截断文件和非零尾部都会报错。源文件和原始备份保持不变。导出失败或不完整时显示具体错误，不再报告操作成功；没有成功导出数据库时不提供空白阅读器入口。

Storloom使用.NET密码学、Windows的`winsqlite3.dll`只读查询、ZstdSharp.Port处理新版压缩消息、K4os.Compression.LZ4处理旧版压缩内容。适配的捕获组件隔离在`Chats/NativeCapture`，许可证见第三方声明。运行时不下载上游工具或执行下载脚本。

| 范围 | 已实现 | 限制 |
|---|---|---|
| 原始备份 | 完整账号目录，包含数据库、WAL与媒体，SHA-256核验及独立清单 | 先退出QQ或微信，不改写客户端目录、不创建联接、不自动删除原件 |
| 微信4.x数据库 | 4096字节页，SHA-512认证，原始32字节密钥或256000轮PBKDF2-SHA512，保留80字节，读取Msg_*与Name2Id及Zstd正文 | 数据结构与密钥机制可能变化，无法解析的会话名退回标识符 |
| 微信3.x数据库 | 64000轮PBKDF2-SHA1，保留48字节，读取MSG文本、XML及有上限的LZ4正文 | 不保证旧版密钥获取，联系人和发送者解析仍有版本限制 |
| NTQQ数据库 | nt_msg.db，1024或0字节封装，4000轮PBKDF2，认证SHA-1与SHA-512组合，私聊与群聊表及消息段 | 不支持旧QQ和每一种Protobuf元素，仅处理已确认的Windows封装锁页例外，其余认证错误拒绝导出 |
| WAL | 头与帧校验、盐、页认证、最后提交帧及数据库大小 | 排除未提交尾部，损坏的已提交帧报错，不提供运行中数据库的一致快照服务 |
| 输出 | 带原始二进制的JSONL、分类消息卡片、完整性报告，跨分片按会话排序 | 仅使用能够读取的联系人资料，不保证每个字段与媒体编码可解析 |

报告中的`Complete`要求发现的受支持消息数据库均成功读取、至少输出一条消息，且未记录未知消息或预期媒体缺失。它不保证所有结构化字段、尚未发现的数据库类别、播放编码或恢复能力。相同消息不会被猜测去重。未知结构、密钥或页错误会失败或标注不完整，不生成虚假的空聊天记录。

## 密钥与一致性快照

QQ也提供显式的“启动 QQ 登录获取”：先退出日常QQ，选择已安装、具有腾讯签名的QQ.exe，再在新建实例中登录。程序核对配套wrapper.node的签名，根据字符串引用与PE函数表定位x64取钥函数，检查实际加载路径和代码后才设置断点，仅接受能通过所选备份认证的候选，不会自动启动调试。这参考[QQDecrypt的Windows方案](https://github.com/QQBackup/QQDecrypt/blob/main/docs/decrypt/extract/NTQQ%20%28Windows%29.md)，调试器改编自MIT许可的chatlog-keeper，已移除密钥日志。上游验证过的版本不代表Storloom已验证所有客户端。登录等待上限90秒，取消或超时会结束独立辅助进程及其调试实例。

界面按选择账号、核验原始备份、导出阅读版引导。原始备份无需密钥；快照完成后可重新登录客户端，用备份数据库验证读取到的密钥。

1. 选择本人拥有的账号目录。自动查找检查当前用户的已知位置，转移的数据可手动指定。容量列统计整个账号及媒体，部分扫描标记为至少值。
2. 必要时在登录状态点击“从已登录客户端读取”。只读当前用户QQ或微信进程内存，查找有上限，候选需通过数据库HMAC认证，不修改目标进程，也不保证每个版本都可找到。部分新版微信登录后不会保留受支持的堆内存形式，此时仍需使用单独的登录调试获取；仅打开客户端并不保证成功。
3. 微信4.x提供单独的登录获取操作。先退出日常微信，选择安装的Weixin.exe，在新子进程中登录。程序验证Weixin.exe和Weixin.dll的本地可信腾讯签名及版本特征，只调试这个新子进程，不附加到已运行的客户端。独立辅助进程获取后退出，Windows随之结束新建客户端树。登录等待上限90秒，辅助进程外层上限两分钟，取消会结束辅助进程。这是显式且依赖版本的操作，日常微信必须事先退出；快照导出仍验证已提交WAL。
4. 也可在隐藏输入框粘贴密钥：微信使用64个十六进制字符，NTQQ使用16或32个可打印ASCII字符。这是聊天数据库的加密密钥，不是QQ或微信的登录密码。命令行从私有`--key-file`读取，不在进程参数中放密钥。捕获密钥不保存、不记日志，可变字节数组用后清零；.NET字符串、系统分页、崩溃转储和用户自行创建的密钥文件不属于完全内存擦除保证。
5. 原始备份必须退出源客户端。核验完成后可重新登录读取密钥，并从离线备份导出。核验清单允许原客户端正在运行或原目录已移除时继续导出。命令行示例：`chat-export --platform WeChat --backup MANIFEST.json --destination NEW_FOLDER --key-file PRIVATE_FILE`。

导出是明文，应像聊天原件一样保护。正常完成、取消和已处理错误后会移除私有工作数据库。系统或进程崩溃可能留下导出目录内的`.work-*`，确认没有导出运行后再检查处理。部分导出报告始终标明不完整，不上传聊天内容。

## 验证与释放空间

自动测试使用合成的QQ和微信加密页、已提交WAL、SQLite消息库、篡改、取消、重复消息与HTML转义，不将私人聊天记录纳入源码或CI。真实客户端登录获取、所有在用版本、大账号性能、联系人媒体解码及恢复兼容性仍需按版本验证。

原始备份与阅读版导出都会保留源文件。以后释放空间前，先核验原始归档并保留清单，再单独审核迁移到新目录，或使用客户端支持的存储管理。程序不会因阅读版存在就判断聊天原件可删除，不提供导出后一键删除账号，也不保证跨版本恢复。

## 会话阅读器

阅读器使用自行实现的C#导出流程和本地HTML、CSS、JavaScript，不嵌入外部导出器。调研参考了[WeChatMsg](https://github.com/LC044/WeChatMsg)、[wxdump_web](https://github.com/xaoyaoo/wxdump_web)和[wechat-decrypt联系人解析](https://github.com/freanocank/wechat-decrypt/blob/main/contacts.py)，借鉴会话导航与备注优先的交互思路，不分发这些阅读器的源码。

微信4的会话表用MD5与Name2Id用户名匹配，各数据库独立解析发送者行号。受支持的联系人表与旧rcontact提供备注、昵称和别名，未知结构使用稳定标识符。NTQQ仅在存在受支持的联系人表时获得名称。

阅读器一次加载300条，通过外部归并排序组织会话，不将全部消息载入内存。JSONL与折叠源码保留消息全文及能够取得的二进制，阅读文本不截断。内容筛选作用于当前页，可取消的下一匹配页查找会继续搜索后续页面。本地媒体按明确引用匹配，以内容哈希复制，支持旧XOR图片。支持可验证的V1图片，以及使用离线派生密钥解码的V2图片。桌面导出会读取当前用户标准微信配置中的图片密钥候选；命令行通过--local-image-keys显式启用。派生密钥只保留在内存中，导出结束后清除。数据库附加字段中的本地标识可补充图片和视频匹配。原图格式不支持时可回退至带说明的缩略图，导出仍标为不完整。WXGF动画、加密表情缓存、VoiceInfo/SILK语音及文档附件的支持见下文；仅有资源索引的引用及其他不支持的图片格式仍明确保留为缺口。媒体不可用增加`unresolvedMedia`，未知消息增加`unsupportedMessages`，任一都会标记阅读版不完整。详见[消息展示范围](message-display.zh-CN.md)。

阅读器用文本节点与JSON序列化，不拼接消息HTML。内容安全策略禁止远程加载。内置WebView2禁用宿主对象、主动下载、权限、框架与外部导航；网页消息仅允许固定来源的受限复制和保存操作，只映射所选归档目录；浏览器备用阅读方式也完全本地运行。

数据库处理使用可配置的1至4个工作线程。普通SQLite读取共享锁，大型带偏移的NTQQ库独占进程级锁页设置。每库与WAL复用AES和MAC上下文，仍逐页认证并验证WAL提交。转移在复制时哈希来源，发布整批前完整核验每个目标，避免冗余读取；移动前再检查两端的机制独立保留。创建原始备份时仍完整核验。阅读版导出先验证数据库密钥，默认再逐文件复查备份。界面可取消勾选复查，命令行从`--backup`导出时可加`--skip-backup-verification`。跳过后仍检查清单、路径、大小、数据库页与WAL认证及复制媒体，但可能漏检其他文件的后续变更。导出报告的`backupReverified`与`verifiedBackupBytes`记录是否执行完整复查，阅读版内容完整不代表已完成跳过的校验。阶段计时与合成性能数据仅用于诊断，不保证机械硬盘或真实客户端的吞吐。

## 微信资源补全

两平台内置表情均统一处理方括号、斜杠及配置中的名称别名。微信加密表情缓存采用从本地配置派生的账号专用 AES-CBC 密钥，密钥仅在内存中使用。PATH 中存在 ffmpeg.exe 时，可将 WXGF/HEVC 动画转换成本地 GIF 预览；转换在独立进程中进行，可取消，并限制运行时间、尺寸和输出大小。FFmpeg 为可选依赖，不随程序分发。转换失败仍明确标记资源不可用，不自动访问私人 CDN 链接。

语音从 media 数据库的 VoiceInfo 读取，使用各库独立的 Name2Id 映射、会话及无符号服务器消息编号精确匹配，拒绝内容冲突的记录。固定版本、单独编译的 SILK 辅助程序转换为 24 kHz 单声道 WAV；缺失或不支持的语音仍标为未解决。文档和压缩附件沿用明确引用匹配、流式复制和内容哈希。资源修补只增加哈希资源及稀疏的阅读器索引关联，不重写 messages.jsonl 或会话分页；原导出报告保留历史统计和不完整状态，原始备份不变。备份中不存在的资源无法还原。

scripts/Build-Silk.ps1 使用 GCC/MinGW 编译 Windows x64 SILK 辅助程序，验证固定上游压缩包的 SHA-256 并保留 MIT 与 Skype SDK 许可。发行包在 GUI 和 CLI 目录中提供辅助程序及许可。参考 [SILK 解码器](https://github.com/kn007/silk-v3-decoder/tree/507be6bca8ce1fb977a061481f1d79e8c610e309)、[表情缓存研究](https://github.com/yanyanbabyi/Wechat-Emoticon-Parser-fix)及[资源库映射](https://github.com/qiaodogbear/ChatTrace)。


## 增量备份与更新阅读版（1.0）

首次使用完整备份。后续在备份步骤选择 **增量备份…**，应用会使用记住的已校验备份，或让你选择上次的备份清单。先退出聊天客户端。新代次复制并校验新增、变更文件；未变化的资源通过清单引用原有副本，数据库和 WAL/SHM 文件则在每个代次一起保存。是否复用依据源文件身份、大小和修改时间；导出前的重新校验开关开启时，会重新计算所有引用文件的哈希。**请保留所有原始备份代次及清单，迁移时一起复制。** 增量代次不是独立完整目录，删除旧的原始代次会使新代次缺少它引用的资源。普通完整备份、普通复制移动的行为不变。

选择新备份，必要时获取与其匹配的数据库密钥，再点 **更新阅读版…**，选择同账号已有的已完成阅读版。更新合并新增和变更消息，保留客户端已经清除的历史消息，复用本地资源，只重建受影响的会话页面。数据库及 WAL 指纹未变时直接跳过；消息优先用服务器 ID 去重，其次使用序号、发送人和时间，无稳定 ID 的消息按内容指纹区分，因此这类消息编辑后会保留为另一条历史记录。首次接入旧阅读版需扫描一次 JSONL 建立磁盘索引，之后复用索引。变更数据库仍需解密、解析，有消息变更时也需要顺序合并现有 JSONL；节省的是对旧消息和附件的重复解析、转换以及无变化页面的重新生成，不保证所有操作即时完成，也不会凭空恢复已过期或缺失的资源。

处理结果先写暂存区，发布前可取消，已有阅读版保留；发布期间出现异常会使用回滚数据，下次更新前恢复中断的发布。更新时请关闭这个阅读窗口，并为 JSONL、派生索引及受影响页面留出工作空间。重要阅读版仍应单独留备份。**继续上次导出** 是恢复同一份不可变备份的中断任务，**更新阅读版** 才是合并新备份。更新报告记录新增、变更、未变消息以及重建会话数；原有导出不完整时，完整性报告仍保守标记。


密码保护、部分加密和暂停／继续的使用方式见[阅读版密码加密](chat-encryption.zh-CN.md)。
