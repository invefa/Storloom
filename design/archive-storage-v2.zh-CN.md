# 归档存储 v2 设计提案

状态: 2.0.0 已接入可选的归档库导入、阅读、索引文字搜索、增量备份、校验和阅览版导出. 不自动迁移或替换现有归档, 不改变正在运行的任务.

## 当前实现范围

- 旧格式: 验证复制后的索引身份重新绑定, 预编译 SQL 复用, 分批持久化首次建库检查点. 检查点与行数据在同一事务提交, 中断后从准确的 UTF-8 字节位置继续.
- 新格式底层: 有界不可变数据包, 内容校验, 父提交链, 最后发布 HEAD, 只遍历未应用的提交后缀. 故障注入验证未发布的数据包不会改变可见提交.
- 查询原型: 持久化 SQLite 投影, 提交游标与数据/搜索索引原子更新, 键集分页. 原始 JSON 字段保留. 中文单字/短词、混合文本和表情通过生成 Unicode 词项并核对原文搜索. 当前采用无位置 FTS5 postings; 仍需更大数据集验证空间成本和查询尾延迟.
- 归档库现已接入导入/续传/更新、文件分块、直接阅读、索引文字搜索及引用定位、增量备份、独立校验、改密码和当前状态的阅览版导出. 存储 API 保持内部接口. 来源更新目前使用完整阅览版, 原始备份增量适配器和归档内部混合保护域仍待实现.
- 当前故障测试覆盖进程内中断和重试, 不等同于断电一致性验证. NTFS/exFAT 的目录项落盘、根提交冗余、损坏恢复和跨进程并发仍待验证. 导入必须主动选择, 保留原始来源, 不能代替独立备份.
- 加密查询原型已改用原维护者提供的 SQLite3MC.PCLRaw 2.6.1, 与旧格式使用的系统 SQLite 隔离. 测试覆盖密文数据库重开、错误密钥拒绝和回滚日志无明文; 对受保护归档缺少二进制查询密钥时直接拒绝, 不回退明文. 原生二进制的来源与许可证已记录, 分发脚本带上相关许可.
- 密钥原型采用随机主密钥, PBKDF2-SHA256 包装密码, 独立域密钥, AES-GCM 认证数据包. 修改密码只重新包装主密钥, 不改写数据包. 更换已泄漏的主密钥需要重新加密, 改密码不能撤销旧密钥副本. 新归档创建支持整体加密, 精细保护仍用于兼容导出的阅览版, 不声称归档内部已支持混合保护域.

### 第二阶段: 核心接入

- 迁移先导入消息, 再保存阅览版文件的逐字节内容, 包括原始 JSONL、未知字段、媒体和其他文件. 不修改或删除源目录. 加密源通过认证解密流读取; 不落地完整明文副本, 且拒绝迁移到无保护的目标.
- 消息检查点保存精确 UTF-8 偏移. 文件检查点保存文件序号与块偏移. 检查点、消息、资源位置和文件进度共同进入提交, 查询缓存可重放恢复. 续迁前检查源清单和文件版本, 源改变时明确拒绝混用快照.
- 当前文件块为 1 MiB, 资源批次最多约 8 MiB 原始字节, 小文件合并打包. 这是待测的内部参数, 不是已冻结格式. 同一保护域的块按内容复用, 私有域使用带密钥的内容标识. 查询缓存仅保存资源位置, 不重复存放媒体字节.
- 文件流支持随机定位. 并发资源流共用最多两个已认证数据包的缓存, 资源字节预算为 16 MiB. 流关闭时清理当前块; 共享缓存的资源缓冲在淘汰或关闭归档时清理.
- 当前读取仍需验证和解密包含目标块的数据包; 跨多个包随机读取大量小资源时的放大成本尚未完成优化和尾延迟验证. 不据此承诺媒体预览性能.
- 备份只复制源提交相对于备份根的新后缀, 不复制查询缓存. 每个新对象按其内容摘要复制并验证, 然后才发布目标 HEAD. 续备份保留当时捕获的提交和已包装密钥元数据; 先完成该快照, 再次备份才收集后来变化. 原备份在中断时仍可读取.
- 独立完整校验是显式操作, 有提交数与字节总量, 支持暂停/取消. 正常打开、消息更新和增量备份不会自动执行整段历史校验.
- 合成测试覆盖普通/加密迁移、消息与文件续迁、最后一个非整块的边界、逐字节恢复、重复块复用、缓存丢失重建、源变化拒绝、加密旧阅览版迁移、增量备份和损坏检测. 迁移与备份仍为串行基线, 并行参数、实际双硬盘测量和原始备份源适配尚未完成. 桌面测试覆盖归档库、导入/导出选项、普通及加密归档直接阅读和原生搜索翻页.

依据: [SQLitePCLRaw 维护者的加密构建说明](https://github.com/ericsink/SQLitePCL.raw/wiki/SQLite-encryption-options-for-use-with-SQLitePCLRaw), [原生加密包维护者文档](https://github.com/utelle/SQLite3MultipleCiphers-NuGet), [SQLite FTS5](https://www.sqlite.org/fts5.html).

### 界面接入

参见 [归档库](../docs/archive-library.zh-CN.md). 原生搜索每批最多 100 条, 使用键集游标. 引用跳转按标识索引定位, 不先生成整个会话的引用表. 兼容导出重新生成当前页面、引用表和 JSONL, 用认证的追加完成日志续传, 避免每处理一个文件都重写增长中的检查点. 导出可选择使用既有加密实现进行完成后保护.

### 初步性能记录

单机本地盘、合成消息、Release 构建的单次观测, 不是跨硬盘或生产归档保证. 100 万条历史基础上追加 100 条时, 只重放 1 个提交. 暂未完成 1000 万条、冷缓存、多轮 p50/p95 和双硬盘测试.

| 测试 | 观测 |
| --- | --- |
| 旧 SQL 封装插入 100 万个消息键 | 24.130 s |
| 预编译语句插入相同消息键 | 6.102 s, 约 3.95 倍 |
| 新数据包和消息/搜索投影首次导入 100 万条 | 36.461 s |
| 追加 100 条及更新消息/搜索投影 | 0.020 s |
| 常见中文词返回前 100 项, 按时间排序 | 506.693 ms |

以上新格式性能观测使用公开域, 不包含源数据库扫描、媒体、密码派生或加密. 加密正确性有单独测试, 加密性能仍须独立测量. 常见词命中量大时, 全局时间排序仍是需要继续优化的路径.

## 目标与取舍

将长期归档与阅览版分开. 原始备份和消息变化记录可独立恢复, 阅读、搜索使用持续维护的数据库, 媒体采用可复用的数据块. HTML/便携阅览包是可重新生成的导出结果, 不再承担主数据库职责.

性能是正确性之外的硬约束. 日常更新不应因为文件复制后标识改变而全量建索引, 不应因新增几条消息而复制整份阅览版, 也不应为了查看加密归档而整体解密. 不以减少认证、丢失原始数据或不安全删除换速度.

这不是将现有目录直接压成一个大文件. 不选择单个巨型 JSONL、单个持续重写的压缩包, 或每条消息一个文件作为主要布局.

## 当前瓶颈对应的改变

| 当前实现 | v2 设计 |
| --- | --- |
| 更新前复制旧阅览版到工作区 | 新提交引用旧数据块, 只增加变化记录和新资源 |
| 扫描历史 JSONL 才能补建消息索引 | 首次导入时同步建立消息索引, 以后按提交持续维护 |
| 用文件标识判断索引能否复用 | 用归档 UUID、提交 ID、索引版本及内容校验判断 |
| 消息发生变化时重写汇总 JSONL | 追加消息版本, 更新相应数据库行和搜索文档 |
| 对变化的来源数据库整库解析 | 适配器提供可靠变化定位时按变化读取, 否则明确降级扫描 |
| 大量媒体小文件与逐文件工作区操作 | 将小对象合并入有界数据包, 大对象分块复用 |
| 加密更新先还原完整阅览版 | 查询时按页、预览时按块解密, 更新只处理变化 |

依据: `ChatReadingUpdate.cs` 当前包含全量旧消息导入及汇总重写; `ChatArchiveWorkflow.cs` 复制旧阅读版本; `ChatIncrementalBackup.cs` 已能按清单引用部分未变化资源, 但数据库文件仍完整复制.

## 逻辑布局

```text
archive/
  format.json                 # 最小格式信息与归档 UUID
  roots/                      # 不可变的已提交根清单, 及冗余提交指针
  packs/                      # 已封存的数据包: 消息变化、原始载荷、资源块
  snapshots/                  # 可选的数据库/索引检查点
  indexes/                    # 可选的可携带查询索引, 可从检查点和变化记录恢复
  tasks/                      # 绑定来源快照的断点与任务计划
  staging/                    # 尚未提交、可继续或清理的写入
```

明文格式信息不放联系人、会话名称、消息内容或密钥. 加密域内的清单、对象映射和检查点同样受保护. 文件名使用不透明 ID. 文件大小、数量和修改时间仍可能暴露活动规模, 不承诺隐藏全部文件系统元数据.

根清单及其引用的数据包是恢复依据. SQLite 查询库保存规范化消息、关联关系、当前视图与全文索引, 持久化保存并按提交追赶. 索引损坏可以重建, 但正常打开和更新不重建. 不把文件路径或文件系统 ID 当作归档身份.

根清单不能每次平铺全部历史对象. 使用可共享未变化节点的持久对象映射, 或检查点加有界增量清单. 新提交只修改受影响节点及其根引用, 对象位置索引保存包 ID、偏移和长度. 否则即使媒体不复制, 重写巨型清单仍会产生与总量相关的瓶颈.

## 消息与身份模型

- 归档、账号和会话使用稳定 ID. 来源目录只是位置, 移动目录不应自动变成新账号.
- 消息键由适配器、账号、会话、原生消息 ID 等可靠字段确定. 缺少稳定 ID 时保留来源行定位及指纹, 标注匹配限制. 不按文本哈希合并两条内容相同的消息.
- 消息版本保留正文、类型、引用、附件关系、原始载荷引用、解析器版本、来源快照与观察时间. 撤回、修改、反应和资源补全追加为版本或事件, 不覆盖原始证据.
- 昵称、备注、群内名称及头像保存版本和来源. 消息可以引用当时实际保存的显示信息. 只有当前资料时记录观察时间, 不伪造历史生效时间.
- 同一图片的多个图源作为资源变体关联, 语音原件、可播放转码、缩略图作为派生关系关联. 派生数据继承来源的保护规则.

查询库至少包含 `messages`, `message_revisions`, `conversations`, `identity_versions`, `resources`, `message_resources`, `source_snapshots`, `import_cursors`, `applied_commits`, `search_documents`.

## 增量导入与来源备份

每次任务固定一个一致的来源快照. 每个来源分片有自己的游标、格式版本与校验信息. 可靠原生序号或变更记录可用于定位新增和修改, 并配合重叠检查处理迟到消息. 不能只用最大时间戳, 否则会漏掉旧消息修改、撤回、反应及资料变化.

没有可靠变化接口时仍可能扫描整个变化数据库. 必须在日志中显示 `来源变化库扫描`, 而不是宣称只读取了新增消息. 此时也不应重新扫描归档中全部历史消息或重新生成全部搜索索引.

缺少可靠文件变化记录的来源还可能需要清点全部文件元数据; 用户选择完整校验时也会产生整批读取. 来源清点、来源数据扫描、归档索引更新分别计数和计时, 不能把归档侧增量与来源侧读取量混为一谈.

原始备份按快照清单保留字节级可恢复信息. 大文件可以按块比较并引用旧块, 新快照不复制未变化资源. 加密来源文件可能因重新加密而出现大范围字节变化, 不承诺所有来源均能获得很高的块去重率. 数据库与其日志文件必须来自一致快照, 不拼接不同时间的文件.

解析器升级有独立版本. 优先重处理受影响的原始载荷或分片, 保留旧解释和来源. 必须整库重解析时将其作为可见的维护任务.

## 数据包与资源仓

初步试验封包目标为 16-64 MiB, 大资源分块目标为 1-4 MiB. 这些是基准测试参数, 不是冻结的格式常量. 控制最坏恢复范围、索引内存、随机读取放大及文件数量, 不能只追求顺序写入速度.

小对象合并写入有界数据包. 已提交包不可原地修改, 单个对象或块有独立边界与校验, 有块位置索引支持范围读取. 不对整个包施加不可随机访问的单一压缩流. 图片、视频等已压缩内容默认不再强压缩; 文本和原始结构化载荷按独立块压缩.

同一保护域内复用内容相同的对象. 加密域使用带密钥的内容标识或不透明 ID, 不直接向明文清单公开私密内容哈希. 不跨公开域和私密域自动共用会暴露内容的对象.

删除、压实与去重回收是单独维护任务. 只处理已知提交的可达关系, 支持暂停. 不在每次更新后自动压实整个归档, 不自动删除原始备份或旧格式数据.

## 持久索引、阅读和搜索

SQLite 保存稳定消息键、会话时间线和 FTS5 全文索引, 在批量事务内维护新增、变化和删除标记. 复用预编译语句, 使用有界内存缓存, 避免逐条准备 SQL 和逐条提交.

SQLite FTS5 是全文索引的候选基础, 但中文检索必须单独验证分词. 候选为中文二元词元加英文词元, 单字使用补充索引或明确限定范围的回退. 正常全局检索不能隐藏一次全历史扫描. 必测中文短词、单字、标点、表情、混合文字与短子串, 也测索引空间放大; 不能只开默认分词器就声称支持全部中文搜索. 参见 [FTS5 官方文档](https://www.sqlite.org/fts5.html).

会话分页采用 `(conversation_id, timestamp, message_id)` 范围查询, 避免超大 OFFSET. 引用跳转直接按稳定消息 ID 定位. 显示条数与实际渲染窗口分开, 阅读器只加载视口附近消息. 搜索先返回有限结果, 支持继续检索和前后方向导航; 解锁后才把私密索引纳入全局搜索.

多媒体预览按块读取, 不为一次预览遍历整个资源仓. 搜索结果、缩略图、转码与预览缓存均纳入加密范围.

## 磁盘与并发策略

权威归档保存在用户指定位置. 对外接盘或慢盘, 可选在本地 SSD 保留加速查询库, 避免让归档盘承担海量 SQLite 随机写. 加速库是可重建副本, 拔掉缓存盘不丢失归档; 加密归档的敏感缓存也必须加密.

流水线采用有界队列: 读取 -> 解析/规范化 -> 压缩/加密 -> 封包 -> 数据库批量写入. 可并行部分允许 1-8 个工作线程, 根据磁盘、CPU 和内存选择默认值. 数据库通常保留单写入者和批量事务, 不为凑线程数制造写锁竞争. 队列满时回压, 不能把整个归档塞进内存.

必要时使用本机 SQLite WAL, 但不将网络共享上的 WAL 当作跨机器同步方案. 使用支持的备份接口生成一致检查点, 不直接复制正在写入的单独 `.db` 文件. Backup API 分步执行不等于只备份变化页面. 参见 [SQLite WAL](https://www.sqlite.org/wal.html) 和 [备份 API](https://www.sqlite.org/backup.html).

本地缓存更新按提交应用变化记录. 可携带索引检查点按恢复成本阈值或用户维护操作生成, 不在每次更新时完整复制. 将归档备份到另一块盘时, 日常传输新增包和清单; 恢复使用最近检查点加后续变化记录. 没有检查点时首次重建的成本应明确显示.

## 提交、断点和崩溃恢复

1. 记录任务输入快照、保护计划与处理游标, 获取归档单写入租约.
2. 向 staging 写入新包及变化记录. 按可验证的对象/批次保存断点.
3. 校验并持久化数据包, 再封存新的不可变根清单. 采用带序号和校验的冗余提交指针, 不依赖一次覆盖写永不损坏.
4. 查询库在事务内应用该提交, 更新 FTS 与 `applied_commit`. 指针和数据库不是一个跨文件原子事务, 必须显式处理两者不一致.
5. 如果根清单已提交而索引落后, 重放缺少的变化记录. 阅读器可暂时服务上一个完整视图并提示索引追赶, 不能把新旧数据混合后标成完成. 多个保护域也必须追到同一可见提交.

只有数据与所需索引均达到目标提交才将更新任务标为完成. 崩溃后以完整清单为准, 未提交的数据包可以继续或回收. 暂停完成当前有界批次后停住, 取消保留已提交批次和游标. 每条来源游标必须绑定来源快照, 不能拿新来源覆盖旧任务继续位置.

保留上一可见提交需要真实的版本行/快照读事务和明确的可见提交标记, 不能只保留一条已被覆盖的 current 行. 查询及搜索结果均按可见版本过滤, 不能因为各保护域分别提交成功就假定跨域原子性.

## 加解密

每个归档生成随机主密钥, 密码通过带版本和参数的 KDF 派生包装密钥, 主密钥再派生或包装各保护域密钥. 不把密码直接当作所有数据文件的唯一长期密钥.

一次解锁在会话内复用已解开的密钥, 避免每个阶段和文件反复执行密码 KDF. 需要内存用量上限和锁定/退出清理; 不把这种内存复用变成自动落盘保存密码.

更改密码通常只重新包装密钥; 密钥泄露后的密钥轮换需要重加密受影响数据, 两者不能混为一谈. 查看、导出密钥是单独的用户操作, 不自动保存密码或原始数据库密钥.

数据块采用有认证的分块加密, 可沿用经审查的 AES-256-GCM 路线. 每次写入保证密钥/nonce 组合不重复, 附加认证数据绑定归档、保护域、对象版本与块序号. 复用已认证的原有密文对象, 不为了快而修改认证规则.

私密查询库采用成熟的加密 SQLite 实现作为候选, 优先评估 SQLCipher, 连同全文索引、WAL 和临时存储一起验证. 需要完成 Windows 构建、许可证、FTS5、依赖体积及兼容性验证后才能确定替换方案. 不能仅加密正文后留下明文搜索索引. 参见 [SQLCipher 安全设计](https://www.zetetic.net/sqlcipher/design/).

阅读归档时按需解密到内存, 不整体解密到工作目录. 来源数据库的解析适配器是否仍需要安全临时区是另一个问题: 未实现按页读取的适配器继续使用明确的安全路径, 不以普通明文临时文件回退.

部分加密采用公开域与私密域分离, 先不为每个会话建立独立数据库. 规则可按会话、类型、发送人、时间及内容选择, 新数据继续匹配已保存规则. 共享对象提供一起保护与严格重打包两种策略, 显示受影响范围. 如果相同内容仍在公开消息里存在, 私密副本不能让那份公开内容消失.

保护范围必须明确是当前视图、历史版本、原始备份还是派生缓存. 迁移中区分未保护、处理中、密文已生成但仍有明文副本、目标范围内迁移完成. 旧副本和旧备份不自动删除, 不能仅因生成密文就宣称所有明文都已消失; 不承诺删除文件等同于介质安全擦除.

将原本公开的数据转入私密域时, 不能只从公开查询库删行: 旧页、全文索引及数据库日志可能仍有内容. 公开查询库可能需要从剩余公开数据重新生成, 清理旧缓存也需明确处理. 这项安全维护可能超过变化量, 必须单独估算和显示, 不能为了宣称部分加密很快而跳过. 从建立归档时就选择合适保护范围可减少后续明文迁移.

## 阅览版与操作逻辑

主流程为建立归档、更新归档、打开归档、导出阅览版和保护设置. 更新直接操作归档, 无需先制作一份完整 HTML 阅览版. 内置阅读器共用同一查询与解密层.

兼容导出保留现有 HTML 路线. 增量导出按消息/会话提交指纹重建受影响的页面及引用摘要, 复用未变化资源, 最后切换清单. 全新导出目录仍需要把用户选定的内容写到该目录, 不能承诺零复制. 静态包全局搜索的性能边界应与内置数据库阅读器区分说明.

保护设置与导出范围在开始前统一呈现. 原始备份密钥与归档保护密码继续区分. 日志展示当前阶段、扫描/复用/变化/写入量、消息数、字节、速度、当前阶段 ETA、实际工作线程及降级原因. 不伪造无法估计的总时间.

## 迁移与性能验收

分阶段落地:

1. 先修复现有格式的索引复用条件, 引入预编译语句、批量断点和明确的全量扫描提示. 这不需要先完成新格式.
2. 建立 v2 原型, 用合成大数据比较现有实现. 验证持久消息/搜索索引及不可变包的读写路径.
3. 接入原始备份、资源引用、内置阅读与搜索, 再接入保护域和导出.
4. 提供可暂停、可继续的一次性旧格式导入. 全量读取旧数据只发生在首次迁移或显式重建. 旧归档保留, 校验完成后用户再选择默认打开哪个.

| 场景 | 必须验证的行为 |
| --- | --- |
| 大归档无变化更新 | 不遍历全部历史消息, 不复制全部媒体, 不重建全文索引 |
| 新增少量消息 | 归档侧工作随变化量增长, 只更新相关索引和页面; 来源全扫单独计时 |
| 修改旧消息/撤回/反应变化 | 不因只看最大时间戳而漏检, 保留旧版本 |
| 打开和引用跳转 | 范围查询与按 ID 定位, 不先读取整个汇总文件 |
| 全局中文搜索 | 覆盖短词、单字、混合文本和加密域, 不解锁时不暴露私密结果 |
| 继续任务 | 重用已提交索引与游标, 不从第 1 条旧消息重新开始 |
| 复制或移动归档 | 归档 UUID、提交及索引有效时仍可复用, 不因文件 ID 改变失效 |
| 更改密码 | 主要成本为密钥包装; 不等同于轮换已泄露的主密钥 |
| 部分加密 | 内容对象及包按受影响范围迁移; 公开索引的必要重建单列, 历史副本和缓存状态可检查 |
| 异常退出/拔盘/磁盘满 | 恢复到完整提交, 不暴露半条消息或未认证数据 |

测试至少覆盖百万与千万消息量级, 大量小附件、少量大视频、NTFS 与 exFAT、低内存及并发阅读. 对比冷缓存和热缓存, 分别记录总耗时、首屏/查询延迟 p50/p95、CPU、峰值内存、实际读写量、写入放大及索引恢复成本. 不用小样本倍数保证真实归档收益.

先验收工作量, 再确定具体秒数: 固定新增 100 条消息, 将历史量从百万增加到千万时, 归档侧不得出现一次额外的全历史遍历. 无变化更新的旧汇总文件读取量、旧媒体复制量及全文索引重建次数应为零. 慢来源扫描单列, 不通过隐藏统计来满足指标. 队列、数据库缓存与解析批次共享受控内存预算, 不能用内存随历史量增长来换取看似稳定的耗时.

原型通过前不冻结包大小、分块大小、缓存容量或导入批次. 格式升级要证明正常增量不重复付出与整个归档规模线性相关的成本, 同时保留完整校验和显式重建路径.
